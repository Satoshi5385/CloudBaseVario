# C言語コーディング規約

本書は、CloudBaseVarioの保守性、移植性、安全性を維持するためのC言語規約である。規則は「必須」と「推奨」を区別する。必須規則への例外は、本書で明示した条件をすべて満たす場合だけ認める。

## 1. 適用範囲

- 必須規則の対象は、プロジェクトが所有する `SRC/**/*.c` と `SRC/**/*.h` とする。
- `tests/`、`tools/`、外部由来の `components/esp_tinyusb/` は本規約の自動監査対象外とする。それぞれの言語規約または上流規約に従う。
- 対象はESP-IDF 6.0.2を使用するESP32-S3ファームウェアである。
- 既存の外部仕様、通信形式、安全判定を、規約対応だけを理由に変更してはならない。

## 2. 書式と命名

### 2.1 必須

- UTF-8、改行、半角スペース4個のインデントを使用し、タブ文字を使用しない。
- 変数名と関数名は小文字スネークケース、定数とマクロは大文字スネークケースとする。
- プロジェクト所有の `typedef` 名は `_t` で終える。
- 時間、電圧、周波数、距離などを保持する識別子には、可能な限り `_ms`、`_us`、`_v`、`_hz`、`_m` などの単位を含める。
- ファイル内グローバル状態は、名前から所有者・意味・単位が明確でない場合、定義の直前にコメントを記載する。

### 2.2 推奨

- ルートの `.clang-format` を使用し、1行100文字を目安とする。
- ファイル固有の著作権テンプレートは要求しない。ファイルの責務が名前から明確でない場合だけ先頭コメントを追加する。

## 3. 型と移植性

### 3.1 必須

- アプリケーションが保持、演算、永続化または通信する整数値には、`uint32_t`、`int32_t` などの固定幅型を使用する。
- ビット演算とシフト演算には符号なし型を使用し、必要な型キャストを明示する。
- SDK、標準Cライブラリ、コールバックABIとの境界では、APIが要求する `int`、`long` などの型をそのまま使用する。
- サイズ、添字、オブジェクト数には、APIと意味が一致する `size_t` を使用してよい。`bool`、列挙型、文字列用の `char` も使用してよい。
- API境界での縮小変換は、値域が検証済みであるか、定義済みの上限によって安全でなければならない。

## 4. 構文と制御フロー

### 4.1 三項演算子（必須）

- 通常のCコードで三項演算子 `? :` を使用してはならない。`if` / `else` を使用し、条件を一度だけ評価する。
- `#define` の置換リスト内だけは、簡潔な定数式またはインライン式に限って許可する。
- コメント、文字列リテラル、文字定数中の `?` は対象外とする。

### 4.2 副作用（必須）

- `++` と `--` を、配列添字、関数引数、代入値、条件式または他の演算の一部へ埋め込んではならない。
- 更新は単独の文とする。ただし、通常の `for` 文の更新節では使用してよい。
- 条件式内で代入してはならない。代入と判定を別の文にする。

### 4.3 制御フロー

- エラーや無効入力はガード節で早期に返すことを推奨する。
- `goto` は関数末尾の一括クリーンアップなど、所有資源を安全に解放する場合だけ使用してよい。
- `switch` の `default` と `if` / `else if` 連鎖の最終 `else` は推奨する。意図的に何もしない場合はコメントを残す。

## 5. 定数と関数設計

### 5.1 マジックナンバー（必須）

- 時間、電圧、周波数、サイズ、回数、しきい値、GPIO、レジスタ値、プロトコル値など、仕様上の意味を持つ数値には名前付き定数を使用する。
- `0` / `1` の初期値や真偽値、配列添字、文字列終端、明白な個数、式自体が意味を示す数学定数は許可する。
- データシート由来の値は、名前付き定数または近接コメントで意味を示す。

### 5.2 関数

- 関数は一つの責務に保ち、過度なネストを避けることを推奨する。
- ローカル変数は宣言時に安全な値で初期化する。直ちに有効な戻り値を代入する場合は、その宣言で初期化してよい。

## 6. ポインタとメモリ管理

### 6.1 ポインタ（必須）

- 公開関数の必須ポインタ引数は、逆参照前に `NULL` を検査する。
- 任意ポインタ引数は、使用前に毎回 `NULL` を検査する。
- SDKコールバック、または呼出し元で検査済みの内部ヘルパーは例外とできる。その場合、非NULL事前条件を関数直前のコメントで明記する。
- ポインタ変数は、有効なアドレスで宣言時初期化できない場合、`NULL` で初期化する。

### 6.2 動的メモリ（必須）

- 周期タスク、繰返し処理、割込み処理内で動的メモリを確保してはならない。
- 起動時初期化、または低頻度で直列化された処理では、サイズ上限があり、所有者と全解放経路が明確な場合だけ許可する。
- 起動時以外の明示的または暗黙的確保には、直前のコメントに `CODING_RULES_DYNAMIC_MEMORY:` を記載し、必要性、最大サイズまたは上限、直列化、解放責任を説明する。
- cJSONなど、呼出したライブラリが内部確保するAPIも同じ規則の対象とする。

## 7. レイヤーと依存関係

- `domain/` はSDK非依存の値型、計算、ポリシーを所有し、`app/`、`platform/`、ESP-IDFヘッダーへ依存してはならない。
- `platform/` はESP-IDF、デバイス、永続化、通信のアダプターを所有し、`domain/` の値型とポリシーを使用してよい。`app/` へ依存してはならない。
- `app/` は起動、タスク、資源、レイヤー統合を所有し、`domain/` と `platform/` を使用してよい。
- 下位処理からアプリケーションへの通知には、コールバック、キュー、イベントビットなどを使用する。
- ハードコードしたレジスタアドレスへ直接アクセスしてはならない。SDKまたはデバイスドライバーAPIを使用する。

## 8. ヘッダー、インクルード、コメント

### 8.1 必須

- 全ヘッダーに `#pragma once` または正しい二重インクルードガードを置く。新規ヘッダーは `#pragma once` を使用する。
- ヘッダーは自己完結させ、公開宣言が必要とする標準型と外部型のヘッダーを直接インクルードする。
- `.c` は対応する自ヘッダーを最初に、その後に標準C、SDK、プロジェクトヘッダーの順でインクルードする。
- ヘッダーに宣言する公開関数には、少なくとも責務が分かるDoxygen形式コメントを付ける。引数、単位、戻り値、NULL許容性が自明でない場合は明記する。

## 9. 自動検査とレビュー

- CIは `SRC/` に対して、タブ、非マクロ三項演算子、埋め込み副作用、未注釈の動的確保、ヘッダーガード、禁止方向の依存を検査する。
- 型の意味、NULL事前条件、マジックナンバー、単位、公開コメントは誤検出を避けるためレビューでも確認する。
- 規約対応後はPythonテスト、ホストCテスト、`git diff --check`、ESP-IDFフルビルドを実行する。
- ビルドと自動テストは実機動作を証明しない。GPIO、LED、音声、BLE、USB、設定保存、OTAは必要に応じて別途実機確認する。

## 付録: `.clang-format`

プロジェクトルートの設定を正本とする。

```yaml
BasedOnStyle: LLVM
Language: Cpp
IndentWidth: 4
UseTab: Never
ColumnLimit: 100
AllowShortFunctionsOnASingleLine: None
BreakBeforeBraces: Attach
SpaceAfterCStyleCast: true
```
