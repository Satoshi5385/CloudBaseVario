# C言語 コーディングルールガイドライン
本書は、プロジェクトの**保守性**および**移植性**を最大限に高め、オープンソース開発において複数の開発者が一貫性のある、堅牢で美しいコードを効率的に記述するための規約である。本規約は、IPA「組み込み向けコーディング作法ガイド（ESCR）」をベースに、現場での実用性を重視して策定されている。

---

## 1. 開発環境と前提条件

* **対象ターゲット:** Raspberry Pi Pico (Pico SDK) / ESP32 (ESP-IDF) 等の32bitマイコン
* **開発環境:** Visual Studio Code (VS Code)
* **基本方針:** * オープンソースプロジェクトとしての可読性と一貫性を最優先とする。
* 規約で縛りすぎず、デバッグや処理効率のための例外認可を認める柔軟な運用を行う。



---

## 2. 基本スタイルと命名規則

### 2.1 インデントと整形

* **インデント:** **半角スペース4つ**とする（タブ文字は禁止）。
* **VS Codeとの連携:** コードの自動整形には `Clang-Format` の使用を推奨する（末尾の付録を参照）。

### 2.2 命名規則 (スネークケース)

識別子は原則として**スネークケース**を用い、役割に応じて大文字・小文字を明確に区別する。

| 対象 | 規則 | 例 | 備考 |
| --- | --- | --- | --- |
| **変数名** | 小文字スネーク | `motor_speed`, `target_temp` |  |
| **関数名** | 小文字スネーク | `read_sensor_data()`, `init_peripherals()` |  |
| **定数・マクロ** | 大文字スネーク | `MAX_BUFFER_SIZE`, `SYS_CLOCK_HZ` |  |
| **型名（typedef）** | 小文字スネーク + `_t` | `config_t`, `state_type_t` | 末尾に `_t` を付与 |

## 3. データ型と移植性の確保

マイコンのアーキテクチャに依存しない高移植性コードを実現するため、標準の基本型（`int` や `long` など）の直接使用は制限する。

### 3.1 固定幅整数型の原則使用

サイズが不整合になりやすい整数型は、`<stdint.h>` で定義されている固定幅整数型を原則使用する。

* **推奨する型:** `uint8_t`, `int8_t`, `uint16_t`, `int16_t`, `uint32_t`, `int32_t`
* **基本型の例外利用:** * データのサイズが動作に影響を与えないループカウンタ（`for (int i = 0; ...)` など）に限り、通常の `int` の使用を認める。
* 文字・文字列を扱う場合は `char` を使用する。

## 4. 構文・制御フローの制限

### 4.1 三項演算子の使用禁止

可読性の低下や、ネストによるバグの混入を防ぐため、**通常のソースコード内での三項演算子（`? :`）の使用は一切禁止**とする。条件分岐はすべて `if-else` 文で記述すること。

* **例外:** マクロ定義内（`#define`）において、簡潔に定数やインライン処理を表現する場合に限り、三項演算子の使用を許可する。

### 4.2 副作用のある式の禁止（評価順序の安全化）

コードの評価順序によるコンパイラ依存のバグを防ぐため、**代入演算（`=`）やインクリメント・デクリメント（`++`, `--`）を、他の演算や条件式と同じ行に混在させてはならない。** 必ず単独の行で実行すること。

```c
// 不可 (評価順序が曖昧になり、バグを誘発する)
array[i++] = ++j;
if (x = get_status()) { ... }

// 良好 (安全かつ明確)
j++;
array[i] = j;
i++;

x = get_status();
if (x != 0) { ... }

```

### 4.3 制御フロー（`goto` や `switch`）の運用

* **goto文:** 積極的な使用は推奨しない。ただし、関数の末尾における「一括エラー処理・クリーンアップ（リソース解放）」など、コードをシンプルに保てる明確なメリットがある場合に限り、リスクを十分に考慮した上での限定的な使用を容認する。
* **switch / if-else:** 状態の考慮漏れを防ぐため、`switch` 文における `default` や、`if - else if` における最後の `else` は、省略せずに記述することを強く推奨する（空処理の場合は `/* 空 */` コメントを残す）。

## 5. 関数設計と定数の運用

### 5.1 関数の規模と構造（早期リターンの推奨）

* **関数の長さ:** 1つの関数は「エディタでスクロールせずに全体が読める長さ」を目安に、肥大化させないこと。
* **早期リターン（ガード句）の推奨:** 無駄なネスト（階層）を深くしないため、エラーチェックや例外的な条件は関数の先頭で速やかに `return` させる設計（早期リターン）を積極的に採用すること。

```c
// 良好な例（早期リターンによりネストが浅く読みやすい）
int32_t process_data(uint8_t *data) {
    if (data == NULL) {
        return ERROR_INVALID_PARAM; // ガード句
    }
    if (!is_system_ready()) {
        return ERROR_NOT_READY;     // ガード句
    }

    // 本処理
    return SUCCESS;
}

```

### 5.2 マジックナンバー（生数字）の完全禁止

コード内に、意味の不透明な生の数値（例: `if (status == 3)` や `delay_ms(50);`）を直接記述することを禁止する。数値は必ず意味のある名前を定義して使用すること。

* 定数定義の方法（`#define`、`const` 変数、`enum`）については、モジュールや用途に応じて適切なものを選択すればよく、一律での制限は設けない。

## 6. ポインタとメモリ管理の安全性

### 6.1 ポインタの安全性（NULLポインタの防御）

C言語で最も致命的となる不正アクセスバグを防ぐため、以下の防御的プログラミングを徹底する。

* **引数のNULLチェック:** ポインタを引数として受け取る関数は、処理の先頭で必ず `NULL` チェックを実施すること。
* **NULL初期化:** ポインタ変数を宣言する際は、即座に有効なアドレスを代入する場合を除き、必ず `NULL` で初期化すること。

### 6.2 動的メモリ確保（`malloc` / `free`）の原則禁止

長期間稼働する組み込みシステムにおけるメモリ断片化（フラグメンテーション）やメモリリークを防止するため、ループ処理内などでの**動的なメモリ確保は原則禁止**とする。

* メモリは原則として静的確保（`static` 配列やグローバル配列）を使用すること。
* **例外ルール:** 起動時の初期化ブロック（`setup` や `app_main` の最初など）において、初期化のためだけに動的メモリを確保することは許容する。また、どうしても動的メモリが必要な場合は、**その必要な理由をコメント等に明記して使用すること**。

## 7. レイヤー設計と依存関係

プロジェクトの保守性と、Pi Pico / ESP32 間の移植性を保つため、ソースコードは以下の3つのレイヤー構造を意識して設計する。

```
【上位】 アプリケーション層 (メインロジック、業務処理)
   │
【中位】 ミドルウェア・制御層 (プロトコル、データ処理、抽象化制御)
   │
【下位】 ドライバ・HAL層 (SDK固有の処理、周辺ペリフェラル制御)

```

### 7.1 階層間の呼び出し規則

* **原則（推奨）:** 依存関係は「上から下」の一方向とする。下位レイヤーから上位レイヤーへイベントを通知したい場合は、直接上位の関数を呼び出さず、コールバック（関数ポインタ）などを利用する。
* **例外認可:** デバッグ処理、あるいはあらかじめ「レイヤー運用適用外」を宣言したモジュール群に関しては、レイヤーを飛び越えた呼び出しや柔軟な相互参照を許可する。

### 7.2 ハードウェア依存コードの分離

* **SDK関数の利用:** 将来的なマイコン変更に対応するため、SPIやI2Cなどの周辺ペリフェラル制御は、制御層で抽象化関数を挟んでカプセル化すること。
* **柔軟な例外:** 単純なGPIO制御（LEDの点滅など）や、標準的なログ出力（`printf`、SDK固有のログ関数）については、アプリケーション層から直接SDKの関数を呼び出してよい。
* **絶対禁止事項:** **レジスタアドレス（ポインタ直接指定）をソースコード内で直接叩く記述は一切禁止**とする。必ずSDKが提供するマクロやAPIを介すること。

### 7.3 ヘッダーファイル（`.h`）のインクルード規則

* **自己完結型ヘッダーの推奨:** ヘッダーファイル内で他の型定義やマクロが必要な場合は、依存関係を隠蔽せず、**ヘッダーファイル内で必要なファイルを積極的に `#include` する**こと。これにより、そのヘッダーを呼ぶだけで必要な定義がすべて揃う状態（自己完結）を維持する。
* **二重インクルードの防止:** すべてのヘッダーファイルにおいて**二重インクルードガードを必須**とする。記述は簡潔性を重視し `#pragma once` を標準とする。

## 8. コメントとドキュメント（Doxygen形式）

オープンソース開発における可読性と、VS Code上での開発体験（ホバー時の説明表示）向上のため、公開関数（ヘッダーファイルに宣言する関数）にはDoxygen形式のコメント記述を必須（または強く推奨）とする。

### 8.1 記述例

```c
/**
 * @brief モーターの目標速度を設定する
 * @param[in] target_speed 設定したい速度 (単位: rpm)
 * @return int32_t 実際の制御に適用された速度、エラー時はマイナス値
 */
int32_t set_motor_speed(int32_t target_speed);

```
